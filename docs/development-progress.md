## 2. 进度记录方式

每项任务分别维护两个状态，避免把“代码已写好”与“已经可用”混在一起。

| 字段 | 可用值 | 记录规则 |
| --- | --- | --- |
| 开发状态 | 待开发 / 进行中 / 代码就绪 / 已实现 / 待研究 / 后续可选 | 开始实现时改为进行中；受新 SDK 限制的代码先记代码就绪 |
| 验证状态 | 未验证 / 基础检查通过 / CI 通过 / 待 27.3 统一验证 / 统一验证通过 / 未通过 | 写清真实验证范围；不能用结构检查替代原生编译或运行 |
| 优先级 | P0 / P1 / P2 | P0 为首版主线；P1 为体验或条件性增强；P2 为后续可选 |
| 证据 | 源码路径、commit、CI 链接或验证记录位置 | 关联到实际交付；外部环境能力只记录已核实的范围 |

维护约定：

1. 后续每次功能提交，同时更新对应任务的开发状态、验证状态与第 9 节记录。
2. 任务编号保持稳定；拆分或调整范围时保留原编号和原因，新增任务继续编号。
3. 提交原生源码后可标记代码就绪、待 27.3 统一验证；只有真实验收通过才能改成统一验证通过。
4. 发现新问题时，在第 8 节登记；修复后关联任务与验证证据，保留历史。
5. 进度按任务和里程碑查看，不以源码行数或任务数量计算功能完成百分比。
6. 本文件记录的是任务进度，不承担后台自动更新或定时跟踪；每轮实际开发、验证后同步维护。
7. 按用户当前安排连续推进任务：每项完成后验证、提交并推送，再继续下一项；27.3 原生统一验证后置。
